## 1. Խաղի մաթ ձևակերպումը

### 1.1 Ռաունդը որպես մեկ քաշում

Ռաունդի ամբողջ արդյունքը որոշվում ա bet-ի պահին. RGS-ը lookup CSV-ից քաշին
համամասնորեն ընտրում ա simulation id ու ֆրոնտին տալիս էդ սիմուլյացիայի
`events` սցենարը [math-sdk.md]։ Mid-round դրամական cash-out ՉԿԱ [D-003,
approval-guidelines.md]։

Մոդելը ձևակերպում եմ «վազքի երկարության» լեզվով, որ պրոտոյի զգացողությունը
պահվի [proto-analysis.md: `curMult = 1 + dist × MULT_RATE`].

- Սահմանում ենք մուլտիպլիկատորների **դիսկրետ սանդղակ** (grid)
  `M = {m_0 = 0, m_1, m_2, …, m_K = wincap}`, որտեղ m_1 < m_2 < … < m_K։
- Ռաունդ = ինդեքսի քաշում. i ~ P (նախաորոշված distribution, per BetMode)։
  `payoutMultiplier = m_i` — book-ում ֆիքսված [math-sdk.md]։
- **Վազքի երկարությունը ածանցյալ ա, ոչ թե պատճառ.**
  `d_i = (m_i − 1) / r`, որտեղ r-ը մուլտի աճի տեմպն ա (պրոտոյի MULT_RATE-ի
  անալոգը)։ Այսինքն նախ քաշվում ա շահումը, հետո հաշվվում ա, թե Dady-ն
  ինչքան ա «վազելու» էկրանին։ Ցուցադրվող մուլտին deterministic ֆունկցիա ա
  անցած տարածությունից — ճիշտ պրոտոյի ոգով, բայց պատճառահետևանքը շրջված ա։
- **Կորուստ (m_0 = 0).** Dady-ն բռնվում ա։ Բռնվելու տարածությունը
  d_catch-ը **ներկայացման ազատություն ա**, ոչ մաթի. այն քաշվում ա
  presentation-only distribution-ից ու payout-ի վրա ՉԻ ազդում։ Սա ա
  «near-miss» ռեժիսուրայի տեղը (տես §1.3)։
- **Շահում (i ≥ 1).** Dady-ն վազում ա մինչև d_i ու «պոկվում ա»
  հետապնդողից (escape) — ներկայացման մեջ դա հին CASH OUT պահի
  համարժեքն ա, բայց ոչ մի կոճակ settlement չի փոխում։

**[Ենթադրություն, ստուգելի]** hold-to-run-ը (պահել/բաց թողնել) մնում ա
որպես տեմպի/կամերայի կառավարում [D-003]. մաթ մոդելի համար այն գոյություն
չունի — d_i-ն ու m_i-ն անփոփոխ են, ինչ էլ խաղացողը սեղմի։

### 1.2 Ինչու grid, ոչ թե «անընդհատ» L

- Lookup-ը վերջավոր սիմուլյացիաների ցուցակ ա (100k–1M per mode)
  [approval-guidelines.md], ուրեմն արդյունքների բազմությունը միևնույն ա
  դիսկրետ ա։ Grid-ը դա դարձնում ա բացահայտ ու ստուգելի։
- Approval-ի «win-սանդղակում դատարկ գոտիներ չլինեն» պահանջը
  [approval-guidelines.md] grid-ի վրա ուղիղ ստուգվում ա. ամեն գոտի պիտի
  բնակեցված լինի ոչ զրո քաշով (տես §4)։
- Optimizer-ը (Rust) աշխատում ա lookup-ի քաշերի վրա [math-sdk.md] — grid-ը
  ֆիքսում ենք մենք, քաշերը բռնացնում ա ինքը։

**[Առաջարկ]** grid-ի քայլը փոքր մուլտերում մանր (որ վազքը սահուն երևա),
մեծերում՝ երկրաչափական (log-հավասարաչափ)։ Օրինակ ձև՝ մինչև 2x քայլը 0.01x,
2x–10x՝ 0.05x, հետո ×1.05 գործակցով մինչև wincap։ Կոնկրետ քայլերը՝
«որոշվելիք» (§3.4)։

### 1.3 Book-ի event-սցենարը

Books ձևաչափը՝ jsonl.zst, ամեն տող `id`, `events` (list<dict>),
`payoutMultiplier` (int, publish-ում fixed-point ×100 — վերջնական ճշտվելու
ա example խաղով) [math-sdk.md]։ Event-երի բովանդակությունը slot-կենտրոն
օրինակներով ա դոկում (`reveal`, `winInfo`, `finalWin`) [math-sdk.md];
**[ենթադրություն, ստուգելի example-games-ով]** event տիպերը խաղը ինքն ա
սահմանում, ֆրոնտի bookEvent→handler շղթան [web-sdk.md] կամայական տիպ
կարա մշակի։

Առաջարկվող event-եր Run Dady-ի book-ում.

| Event | Դաշտեր | Դերը |
|---|---|---|
| `runStart` | `mode`, `rate` (r), `finalDistance`? | Ռաունդի բացում. ֆրոնտը գիտի ինչ ա նվագարկելու |
| `runProgress` | `index`, `distance`, `mult` | Հենակետ ամեն «գոտու» անցնելիս. սրանք են `/bet/event`-ով էջանշվում, որ ընդհատված ռաունդը resume լինի ճիշտ տեղից [rgs-api.md] |
| `nearMiss` | `intensity`, `distance` | Ներկայացման հուշում. հետապնդողը մոտենում ա։ Payout-ի վրա չի ազդում — ռեժիսուրա ա |
| `escape` | `distance`, `mult` | Շահումով ավարտ. Dady-ն պոկվում ա |
| `catch` | `distance` | Կորստով ավարտ. բռնվեց։ `distance`-ը presentation-քաշումով ա ընտրված գեներացիայի պահին |
| `finalWin` | `amount` (mult) | Վերջնական շահում. ՊԻՏԻ խիստ համընկնի `payoutMultiplier`-ի հետ (hash-ստուգում) [math-sdk.md] |

Երկու դիտողություն.

1. **`runProgress`-ի խտությունը** trade-off ա. շատ event = մեծ books ֆայլ
   (սահմանը 4.2GB/ֆայլ, 10M events/mode [approval-guidelines.md]), քիչ
   event = կոպիտ resume։ **[Առաջարկ]** հենակետ միայն գոտիների սահմաններին
   (log-սանդղակով ~40–80 հատ max win-ի ճամփին), ոչ ամեն կադրին։
2. **`nearMiss`-ը գեներացվում ա մաթ կոդում, բայց մաթ չի.** այն դետերմինիստիկ
   դրվում ա սցենարի մեջ գեներացիայի պահին (sim id-ով seed-ած RNG
   [math-sdk.md], ուրեմն վերարտադրելի ա), ու Bet Replay-ում նույնությամբ
   կնվագարկվի [approval-guidelines.md]։ Դիզայնի հարցը՝ §5։

### 1.4 Կապը RGS հոսքի հետ

Մեկ ռաունդ = մեկ debit (`/play`, amount × mode-ի cost) ու մեկ credit
(`/end-round`) [rgs-api.md]։ «Continue»-ի ոչ մի երկրորդ debit չկա — D-003-ը
սա փակել ա։ `auto_close_disabled` դրոշի կարիքը (երկար ռաունդ, ձեռքով
end-round [math-sdk.md]) որոշվում ա T-0003-ի հետ համատեղ. **[առաջարկ]**
քանի որ ռաունդը վայրկյանների կինո ա, default-ը (RGS-ը ինքն ա փակում)
հավանաբար բավական ա, բայց սա Տիգրանի հետ ճշտելու կետ ա։

## 2. BetMode կառուցվածքի տարբերակներ

Շրջանակը [approval-guidelines.md]. base mode = 1.0× cost, ամենաէժանը;
ամեն mode-ի RTP ∈ [90.0%, 96.7%]; mode-երի RTP տարբերությունը ≤ 0.5
տոկոսային կետ; cost multiplier ≤ 2,000×; base mode std dev ≥ 0.6։
Pre-bet ռիսկ-ընտրությունը legal ա [dev չաթ 19:52, approval-guidelines]։

Կարևոր ֆոն. **մաթը release-ից հետո սառած ա** [approval-guidelines.md] —
mode-երի քանակը launch-ի որոշում ա, «հետո կավելացնենք» տարբերակ,
ամենայն հավանականությամբ, ՉԿԱ (ստուգելու հարց՝ §5.1)։

### Տարբերակ A — միայն base (1 mode)

Մեկ mode, cost 1.0×, մեկ distribution։

- **Կողմ.** Ամենափոքր certification մակերեսը. cross-mode spread-ի
  պահանջը տրիվիալ բավարարված ա, մեկ optimization, մեկ sim փաթեթ,
  ամենաարագ ճամփան մինչև submit։
- **Դեմ.** D-003-ի «խաղացողի իրական ընտրությունը pre-bet BetMode-երով ա»
  միտքը մնում ա չիրացված — խաղացողի ձեռքին ընտրելու ոչինչ չկա, «short
  run / long run» գաղափարը կորում ա։ Ու քանի որ մաթը սառչում ա,
  հետո ավելացնել չենք կարող։

### Տարբերակ B — base + «Երկար վազք» (2 mode) — **նախընտրածս**

1. **`base`** — cost 1.0×։ «Կարճ վազքի» պրոֆիլ. հաճախ, համեստ շահումներ,
   մուլտի մարմինը ցածր գոտում, պոչը՝ չափավոր։ Std dev ≥ 0.6-ը սա պիտի
   տա (critical թեստ ա [approval-guidelines.md])։
2. **`long_run`** — cost > 1.0× **[որոշվելիք, օր. 1.5×–5× միջակայքից]**։
   «Երկար վազքի» պրոֆիլ. կորուստներ ու ցածր շահումներ ավելի հաճախ, բայց
   մարմինը ձգված դեպի բարձր մուլտեր, ծանր պոչ, max win-ի ամբողջ
   ներուժը էստեղ ա։ RTP-ն base-ից ≤ 0.5 կետ տարբեր [approval-guidelines.md]։

- **Կողմ.** Pre-bet ընտրությունը իրական ա ու թեմատիկ («ինչքա՞ն ես
  պատրաստ վազել»), երկու optimization-ը կառավարելի ա, spread-ի
  պահանջը երկու mode-ի արանքում պահելը շատ ավելի հեշտ ա, քան երեքի։
  Երկու mode-ը նաև Bet Replay-ի review-ի event-ID ցուցակը (normal/big/
  max win/loss [approval-guidelines.md]) պարզ ա պահում։
- **Դեմ.** Մեկ ընտրություն ա, ոչ սպեկտր; long_run-ի dead-spin բաժինը
  պիտի զգույշ պահվի (§4.6), որ «զրոների գերակշռություն» մերժման հիմքի
  տակ չընկնի [approval-guidelines.md]։

### Տարբերակ C — base + 2 պրոֆիլ (3 mode)

`base` (1.0×), `sprint` (ցածր վոլատիլություն, շատ մանր շահումներ),
`marathon` (ծանր պոչ, հազվադեպ մեծ շահումներ)։

- **Կողմ.** Ընտրության լիարժեք սպեկտր, ամեն խառնվածքի խաղացողին իր կորը։
- **Դեմ.** Երեք distribution + երեք optimization + երեք 100k–1M sim
  փաթեթ; ≤0.5 կետ spread-ը երեք mode-ի վրա միաժամանակ պահելը
  optimization-ի վրա կրկնակի ճնշում ա; sprint-ի «շատ մանր շահումներ»
  պրոֆիլը std dev-ի ու «win-սանդղակի դատարկ գոտիներ» պահանջների հետ
  լարվում ա; review մակերեսը (3 reviewer-ի ձեռքին 3 mode) մեծանում ա։
  Առաջին խաղի համար՝ շատ ա։

### Իմ առաջարկը — B

Փաստարկը. D-003-ի ոգին (իրական pre-bet ընտրություն) իրացվում ա մեկ
հստակ, թեմատիկ որոշումով, իսկ մաթ/QA/review ծախսը մնում ա առաջին
պրոդուկտին վայել։ A-ն ընտրությունը սպանում ա ընդմիշտ (freeze-ի
պատճառով), C-ն ռիսկն ու ծավալը կրկնապատկում ա այն պահին, երբ դեռ մեկ
խաղ approval-ից անցկացրած չունենք։ Եթե հիմնադիրը C ա ուզում՝ մաթ
առարկություն չունեմ, միայն ժամկետային ու approval-ռիսկի։

## 3. Crash-point distribution-ի ընտանիքը

Այս բաժնում ֆիքսում եմ **ձևերն ու կապերը**, ոչ թվերը։ Բոլոր թվային
միջակայքերը «որոշվելիք» են (§3.4), վերջնականը դուրս ա գալու optimization-ից
ու սիմուլյացիայից, վավերացնում ա հիմնադիրը։

### 3.0 Նշանակումներ

Lookup-ի քաշերից w_i (uint64 [math-sdk.md]) ստացվում ա նորմավորված
հավանականություն `p_i = w_i / Σw`։ Mode-ի cost-ը c։ Այստեղ բոլոր
մուլտերը բազային bet-ի նկատմամբ են. RTP-ի ու պահանջների ստուգումը՝
mode-ի cost-ին հարաբերած (տես §4.1)։

### 3.1 Կմախքը՝ երեք բաղադրիչ + զրո

Payout distribution-ը per mode.

```
P(M = 0)        = p_dead                     (բռնվել)
P(M = m_i)      = (1 − p_dead) · f(m_i)      (i = 1…K−1, շահման մարմին+պոչ)
P(M = wincap)   = p_cap                      (ատոմ max win-ին)
```

որտեղ f-ը խառնուրդ ա.

```
f(m) = (1 − ε) · f_body(m) + ε · f_tail(m)
```

- **f_body — երկրաչափական/դիսկրետացված էքսպոնենտ.** grid-ի ինդեքսի վրա
  `f_body(m_i) ∝ exp(−λ · d_i)` (d_i-ն վազքի երկարությունն ա)։ Սա բնական
  «crash» զգացողությունն ա. ամեն հաջորդ մետրը գոյատևելու մոտավոր հաստատուն
  hazard։ λ-ն որոշում ա բնորոշ վազքի երկարությունը → median mult-ը։
- **f_tail — ծանր պոչ (դիսկրետացված Pareto/zipf).** `f_tail(m_i) ∝ m_i^(−α)`
  բարձր գոտում։ Առանց սրա մեծ մուլտերը կա՛մ անհասանելի են, կա՛մ
  win-սանդղակում դատարկ գոտիներ են առաջանում [approval-guidelines.md]։
  α-ն որոշում ա, թե ինչ արագ ա պոչը մարում; ε-ը՝ ինչ բաժին ա պոչին։
- **p_cap ատոմ.** max win-ը պիտի «իրատեսորեն հասանելի» լինի (տիպիկ
  >1/10,000,000 [approval-guidelines.md]) — բացահայտ ատոմը դա երաշխավորում
  ա ու optimization-ում wincap quota-ով առաջինն ա ամրացվում [math-sdk.md]։

### 3.2 Կապերը թիրախների հետ (ճշգրիտ, ոչ սիմուլյացիոն)

Քաշերից ամեն ինչ հաշվվում ա փակ տեսքով.

```
RTP        = E[M] / c = (Σ_i p_i · m_i) / c
hit-rate   = 1 − p_dead                        (ոչ զրո շահման հաճախություն)
Var[M]     = Σ_i p_i · m_i² − (Σ_i p_i · m_i)²
std dev    = √Var[M] / c                       (հարաբերած bet cost-ին)
```

**[Ենթադրություն, ստուգելի]** std dev ≥ 0.6 պահանջի ճշգրիտ նորմավորումը
(bet-ի՞, թե՞ cost-ի նկատմամբ) approval-guidelines-ի էջում ա ամբողջական
աղյուսակներով — մինչև ACP login-ով checklist-ը կարդալը հաշվում ենք
երկու ձևով էլ ու պահում ավելի խիստը։

Ինտուիտիվ կապերը, որ պարամետրերը շարժելիս պիտի հիշվեն.

- λ ↑ → կարճ վազքեր, median mult ↓, variance ↓
- ε ↑ կամ α ↓ → պոչը ծանրանում ա, variance ↑, բայց նույն RTP պահելու
  համար մարմինը/hit-rate-ը պիտի տեղի տա
- p_dead ↑ → hit-rate ↓, variance ↑ (ամբողջ RTP-ն քիչ դեպքերի վրա ա)
- p_cap-ը RTP-ին ավելացնում ա `p_cap · wincap / c` — wincap 500,000×-ի
  մոտ նույնիսկ 10⁻⁷ ատոմը ~0.05 RTP-կետ ա (÷c), սա հաշվի մեջ ա մտնում

### 3.3 Ինչ ա անում optimizer-ը, ինչ ենք անում մենք

Math SDK-ի հոսքով [math-sdk.md]. մենք distribution-ում սահմանում ենք
criteria/quota (wincap, 0-win, win-դասեր), ամեն win-դասի 3 պարամետրից
(RTP-բաժին, միջին win, hit-rate) տալիս ենք 2-ը, Rust optimizer-ը քաշերն
ա բռնացնում թիրախ RTP-ին։ Այսինքն §3.1-ի f-ը մեր «նախնական ձևն» ա
(սիմուլյացիաների գեներացիայի բաշխումը), իսկ վերջնական p_i-ն optimizer-ի
output-ն ա. **մեր պարտքն ա ձևն ընտրել այնպես, որ optimizer-ը այն
չաղավաղի** (օր. դատարկ գոտի չբացի)։ Ստուգումը՝ §4.5։

## 4. Հաշվարկելի սահմանափակումներ (ինչ ենք ստուգելու)

Ամեն build-ի հետ գնացող ստուգացանկ. ամեն կետ՝ կա՛մ ճշգրիտ հաշվարկ
քաշերից, կա՛մ սիմուլյացիա, երկուսի դեպքում էլ՝ script, ոչ ձեռք։

1. **RTP ճշգրիտ** — lookup-ի քաշերից փակ բանաձևով (§3.2), ամեն mode.
   ∈ [90.0%, 96.7%], ու բոլոր mode-երի max−min ≤ 0.5 կետ։ Սիմուլյացիան
   (1M) նույն թիվը պիտի տա վիճակագրական սխալի սահմանում — երկուսն էլ
   հաշվում ենք, շեղումը լոգ ա գրվում։
2. **Hit-rate** — 1−p_dead ≥ 1/50 ամեն mode-ում, ճշգրիտ քաշերից։
3. **Std dev** — base mode ≥ 0.6, ճշգրիտ քաշերից (§3.2-ի նորմավորման
   վերապահումով)։
4. **Cap-եր** — max(m_i) ≤ 500,000×; ամեն mode-ի cost ≤ 2,000×; base-ը
   1.0× ու ամենաէժանը։
5. **Win-սանդղակի ամբողջականություն** — optimization-ից ՀԵՏՈ ամեն
   գոտում (log-bucket-ներ 0.1x-ից մինչև wincap) Σw > 0. դատարկ գոտի =
   fail [approval-guidelines.md]։ Plus wincap-ի հասանելիություն՝
   p_cap > 0 ու «տիպիկ >1/10M» շեմի համեմատում։
6. **Dead spin-երի բաժինը** — p_dead-ը ամեն mode-ում ստուգվում ա բացահայտ
   շեմով **[որոշվելիք, բայց ≪ 0.9. 90k/100k զրոն մերժման հիմք ա
   approval-guidelines-ում]**։
7. **ETL / CVaR / tail probabilities / exposure** — non-critical թեստերը
   submit չեն արգելում, բայց tier են իջեցնում [approval-guidelines.md]։
   Հաշվում ենք CVaR-ը մի քանի մակարդակի վրա ու պոչի հավանականությունները
   սիմուլյացիայից; շեմերի աղյուսակների ճշգրիտ արժեքները approval էջից
   ենք վերցնելու (մի մասը login-ի ետևում ա — Q-003), մինչև էդ ռեպորտում
   թվերը տպում ենք առանց pass/fail վճռի։
8. **Ֆայլային սահմաններ** — events ֆայլ ≤ 4.2GB, ≤ 10M events/mode
   [approval-guidelines.md]. runProgress-ի խտության ստուգումն էստեղ ա։
9. **Consistency** — books-ի `payoutMultiplier` ≡ lookup 3-րդ սյուն
   (hash-ստուգում [math-sdk.md]); `finalWin` event ≡ payoutMultiplier;
   publish ձևաչափի ×100 fixed-point-ի ստուգում example խաղի դեմ։
10. **Վերարտադրելիություն** — նույն sim id → նույն book (RNG seed
    sim-ով [math-sdk.md]). Bet Replay-ի պահանջի մաթ կողմն ա։

## 5. Բաց հարցեր հիմնադրի ու թիմի համար

1. **Mode-երի քանակը launch-ին (A/B/C, §2).** Իմ առաջարկը B-ն ա։
   Կապված հարց Սևակին/Տիգրանին. մաթի post-release freeze-ը
   [approval-guidelines.md] նշանակո՞ւմ ա, որ նոր GameVersion-ով էլ mode
   ավելացնել չի լինի, թե՞ նոր version = նոր submit։ Սա A-ի ռիսկը
   որոշող փաստ ա — docs-ում ուղիղ պատասխան չկա։
2. **Max win թիրախը.** Cap-ը 500,000× ա, բայց դա թիրախ չի։ 1,000×-ը
   «համեստ crash» ա, 10,000×-ը մարկետինգային թիվ ա, բայց RTP բյուջեից
   ավելի ա ուտում ու exposure թեստերին ա դիպչում։ Ի՞նչ ենք ուզում, որ
   Run Dady-ի «երազանքի շահումը» լինի։
3. **Near-miss զգացողությունը.** Կորստի դեպքում catch-ի distance-ը
   ազատ ենք ընտրում (presentation)։ Դիզայնի հարց. ուզո՞ւմ ենք բռնվելը
   հաճախ «քիչ էր մնում» գոտում լինի (դրամատիկ, բայց agression-ի ռիսկ),
   թե՞ ազնիվ համաչափ վազքի բնական պրոֆիլին։ Նաև ստուգելու հարց՝ կա՞
   Stake-ի կանոն near-miss ռեժիսուրայի մասին — docs-ում չեմ տեսել,
   Սևակին խնդրում եմ աչքի տակ պահի example-games/certification նյութերում։
4. **Sub-1× շահումներ.** RGS դոկը <0.1x win-երի ցուցադրման ճշտություն ա
   սահմանում [rgs-api.md], այսինքն հարթակում 1×-ից փոքր շահումներ
   գոյություն ունեն։ Ուզո՞ւմ ենք Run Dady-ում «կիսափախուստ» (բռնվեց, բայց
   bet-ի մի մասը ետ եկավ)՝ dead spin-երի բաժինը իջեցնելու համար, թե՞
   մաքուր 0-կամ-շահում դրամատուրգիա։ Մաթ կողմից sub-1× գոտին dead-spin
   ու hit-rate թեստերը մեղմացնում ա, բայց «escape»-ի իմաստը ջրիկացնում ա։
5. **long_run-ի cost-ը (եթե B).** 1.5×–5× միջակայքից որտե՞ղ ենք դնում —
   սա պրոդուկտի positioning ա (ինչքան «թանկ ա տոմսը» երկար վազքի)։
6. **RTP թիրախի ճշգրիտ թիվը.** [90.0, 96.7] պատուհանից որտե՞ղ ենք
   կանգնում։ Բարձր RTP = ավելի «առատաձեռն» զգացողություն ու մրցունակ
   positioning, ցածր = ավելի մեծ մարժա։ Առևտրային որոշում ա, հիմնադրինը։
7. **Հենակետային event-երի ձևաչափը** (runProgress/near-miss դաշտերը) —
   Տիգրանի հետ համաձայնեցնելու ա T-0003-ի bookEvent handler-ների հետ,
   որ մաթն ու ֆրոնտը նույն բառարանով խոսեն։
